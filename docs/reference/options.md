# Module Options Reference

This reference documents the caisson framework's module options. All descriptions are sourced from the Nix-native `description` fields in the module code.

For `lib.caisson` functions, see [Library Reference](./lib.md).

The options are declared by the `core` module of caisson, which is imported into an evaluation of an integrated class. In an evaluation whose library is not a caisson composition, such as a home-manager configuration that the NixOS module of home-manager embeds, the `core` module declares nothing.

## Options

### `caisson.manifest`

- **Type:** `lib.caisson-core.types.manifest` (read-only)
- **Default:** the composed library's `caisson-core.evalManifest`, or its `caisson-core.libManifest` in an evaluation that has none
- **Source:** `modules/generic/core/caisson/manifest.nix`

The manifest of this evaluation result: its `type`, `name`, `parent` and `children`, and the registries and declared facts of the composition it is declared under, which are `dependencies`, `defaultEcosystemSrc`, `systems` and `projects` as given to `mkLib`, plus the registered `libOverlays` and `modules` dictionaries (project entries under `<project>/<name>`, locals winning). Structural, flake-parts and NixOS configurations have a manifest. Reading it type-checks the manifest; the `flake.modules` and `flake.libOverlays` outputs are drawn from it, and flake-parts' `systems` defaults to the manifest's `systems`, the empty list when the composition declares none, so such a flake has no per-system outputs (`modules/flake/core/caisson/systems.nix`).

### `caisson.<integration>.configurations`

- **Type:** lazy attribute set of `lib.caisson.<integration>.types.configuration`, read back as manifests
- **Default:** `{ }`
- **Source:** `lib.caisson.<integration>.configurationsModule`, generated by `mkIntegration` in `lib-overlays/integrations/default.nix`

The configurations of an integration declared inside this configuration, by name. The option is declared by the module of the integration, `lib.caisson.<integration>.configurationsModule`. For the integrations of caisson, the `core` module of caisson declares it instead, through a module shared by all of them (`lib.caisson.integrations.configurationsModuleFor`). An entry takes what that integration's `mkConfiguration` returns, a function of `{ name, parent }`, and reads back as the finished manifest:

```nix
{ config, lib, ... }:
{
  caisson.structural.configurations.inner = lib.caisson.structural.mkConfiguration { };
}
```

Each entry is finalized when it is read, with the attribute it is declared under as its name and the childless manifest of this configuration as its parent. An entry of an integration that evaluates a configuration per system (nixos) reads back as its evaluation results by system, `config.caisson.nixos.configurations.laptop.x86_64-linux`, a manifest for each system the configuration is evaluated for. The names are known without finalizing anything, so `builtins.attrNames config.caisson.structural.configurations` evaluates no configuration.

A configuration declared inside this configuration reads the result of its childless evaluation, which leaves out the configurations declared inside it. In the childless evaluation an entry's result is not readable, and reading it fails with a message saying so. A definition that reads an entry is therefore written under `!lib.caisson.evalManifest.childless`:

```nix
# an option of this configuration, defined from a configuration declared inside it
innerGreeting =
  if lib.caisson.evalManifest.childless then
    null
  else
    config.caisson.structural.configurations.inner.value.config.greeting;
```

A module that only declares configurations needs no such test. What the configurations declared inside it export is passed up without that test, through `caisson.<integration>.exported` below.

An entry that is not a configuration, or is a configuration of another integration, is refused. The type of an entry is the configuration type of the integration, so the refusal names the option and the file that defines the entry. It also names the option that takes a configuration of that integration. The type reads the integration of an entry from the `type` of its manifest when the entry is finalized. Structural, flake-parts and nixos configurations can be declared. A configuration of an integration that evaluates a class another integration owns is declared as a configuration of the integration that owns the class: `lib.caisson.nixos-minimal.mkConfiguration` returns a nixos configuration, declared under `caisson.nixos.configurations` and published with the others. The constructors of the remaining integrations return an evaluated value. A configuration can hold configurations of any integration declared inside it.

### `caisson.<integration>.exported`

- **Type:** function from the configurations declared to an attribute set of them
- **Default:** `configurations: configurations`, every configuration declared
- **Source:** `lib.caisson.<integration>.configurationsModule`, generated by `mkIntegration` in `lib-overlays/integrations/default.nix`

Function that selects which of the configurations declared under `caisson.<integration>.configurations` this configuration passes up. What each selected configuration exports (its `outputs.exports`: `lib`, `libOverlays`, `modules`, `pkgOverlays`) is merged into this configuration's `caisson.exports`, beside what the registry selectors here choose. A configuration declared inside passes up, in turn, what the configurations declared inside it pass up, so the exports of nested structural configurations are passed up to the caisson top with nothing written:

```nix
{ lib, ... }:
{
  caisson.structural.configurations.impl = lib.caisson.structural.mkConfiguration { };
}
```

The configurations themselves are passed up as well, each with its path, and the caisson top publishes them under the output attribute set their integration declares, named from the paths:

```nix
{ lib, ... }:
{
  caisson.nixos.configurations.laptop = lib.caisson.nixos.mkConfiguration { };
}
```

publishes `nixosConfigurations.laptop` from a flake-parts or structural caisson top. A name that is alone stays bare. Names that collide gain the segments that tell them apart, from the segment nearest the caisson top: `host-1` declared in the structural configurations `a` and `b` is published as `a/host-1` and `b/host-1`, and a configuration evaluated for several systems as `x86_64-linux/laptop` and `aarch64-linux/laptop`. Configurations that still share a name are refused, with their paths. An integration may give its configurations a different name first: a home-manager configuration declared as `chris` inside the NixOS configuration `laptop` is published as `homeConfigurations."chris@laptop"`.

`caisson.structural.exported = _: { };` passes up none, and a selector returning a subset passes up those. The merge is made in the full evaluation, which holds the configurations. It is absent from the result of the childless evaluation, and from an evaluation result that has no manifest.

The caisson top records what it published in the export record, `exportRecord` of the manifest it publishes as `caisson.manifest`, keyed as the outputs are. The entry for a name holds the path to the configuration by the names declared, the sentences that say how the name came about, and the positions of the code that made it, among them the file that defines this selector when it is not left at its default.

### `caisson.<integration>.exportNote`

- **Type:** null or string
- **Default:** `null`
- **Source:** `lib.caisson.<integration>.configurationsModule`, generated by `mkIntegration` in `lib-overlays/integrations/default.nix`

A sentence saying what `caisson.<integration>.exported` does to the configurations it passes up, for a selector that does more than pass every configuration up unchanged. The caisson top adds it to the notes of the export record entry of each name published from those configurations, after the notes of the configurations declared inside it:

```nix
{ lib, ... }:
{
  caisson.nixos.configurations = {
    nas-1 = lib.caisson.nixos.mkConfiguration { };
    lab-3 = lib.caisson.nixos.mkConfiguration { };
  };
  caisson.nixos.exported =
    configurations:
    lib.mapAttrs' (name: lib.nameValuePair "office-${name}") (
      lib.filterAttrs (name: _: !lib.hasPrefix "lab-" name) configurations
    );
  caisson.nixos.exportNote = "office configurations carry the site prefix; lab configurations stay unpublished";
}
```

publishes `nixosConfigurations.office-nas-1`, and its entry in the export record holds the note.

### `caisson.home-manager.activation.usersDeclaredElsewhere`

- **Type:** `listOf str`
- **Default:** `[ ]`
- **Source:** `modules/nixos/home-manager-activation/`
- **Declared in:** a NixOS configuration that imports `caisson/home-manager-activation`, which `caisson/default` for the `nixos` class does

The users that have an account on the system of this NixOS configuration although `users.users` does not declare it.

A NixOS configuration activates the home-manager configurations declared inside it. It expects the account of the user of each home-manager configuration in `users.users`, and it refuses a home-manager configuration whose user has no account there. Such a home-manager configuration is usually a mistake: a misspelled user name, or a home-manager configuration declared inside the wrong NixOS configuration.

An account that systemd-homed manages is not in `users.users`. systemd-homed keeps the record of the account, and the NixOS configuration must not declare it a second time. List the user here:

```nix
{ lib, ... }:
{
  services.homed.enable = true;

  caisson.home-manager.activation.usersDeclaredElsewhere = [ "chris" ];

  caisson.home-manager.configurations.chris = lib.caisson.home-manager.mkConfiguration {
    configModule = {
      home.homeDirectory = "/home/chris";
    };
  };
}
```

The home-manager configuration of a listed user is not refused. It is activated by a user unit that runs when the user logs in, which is when systemd-homed mounts the home directory. The home-manager configuration sets its home directory itself, because the NixOS configuration has no account to read it from.

A user that is listed here and also declared in `users.users` is refused, because the two statements contradict each other.

See [`modules.nixos."caisson/home-manager-activation"`](./lib.md#modulesnixoscaissonhome-manager-activation) for the units.

### `caisson.useUserPackages`

- **Type:** `bool`
- **Default:** `false`
- **Source:** `modules/homeManager/nixos-parent/`
- **Declared in:** a home-manager configuration that imports `caisson/nixos-parent`, which a home-manager configuration declared inside a NixOS configuration imports by default

Whether the NixOS configuration installs the packages of this home-manager configuration in `/etc/profiles/per-user/<user>`.

When it is false, the activation of the home-manager configuration installs its packages, `home.path`, into a Nix profile in the home directory, `~/.nix-profile`. The activation runs as the user, and it can write the home directory only while the home directory is mounted and unlocked. On a computer whose home directories are encrypted, or managed by systemd-homed, that is only while the user is logged in. A switch to the NixOS configuration then changes the packages of the user at the next login.

When it is true, the NixOS configuration builds `/etc/profiles/per-user/<user>` from `home.path` as part of the system. Every switch to the NixOS configuration changes the packages, whether the user is logged in or not. NixOS puts `/etc/profiles/per-user/$USER` on the `PATH` of every login shell:

```nix
{ lib, ... }:
{
  services.homed.enable = true;

  caisson.home-manager.activation.usersDeclaredElsewhere = [ "chris" ];

  caisson.home-manager.configurations.chris = lib.caisson.home-manager.mkConfiguration {
    configModule = {
      home.homeDirectory = "/home/chris";
      caisson.useUserPackages = true;
    };
  };
}
```

home-manager's NixOS option `home-manager.useUserPackages` does the same for every home-manager configuration it embeds. The caisson option sets the home-manager option `submoduleSupport.externalPackageInstall` of a single home-manager configuration, and the NixOS configuration installs `home.path` for that home-manager configuration.

With the option set, the home-manager commands show this:

| Command | What it shows or does |
| --- | --- |
| `home-manager generations` | the generations of the home-manager profile in the home directory, as without the option; the activation records a generation each time it activates a new version |
| `home-manager switch` | links the files of the version it builds and records its generation; the packages of that version are installed for the user at the next switch to the NixOS configuration. When that version is the version the NixOS configuration activated, it activates the same generation and warns of nothing. When its `home.path` differs from the `home.path` the NixOS configuration installed, the activation prints a warning that the `packages` profile holds another version (see [`caisson.drift.warn`](#caissondriftwarn)) |
| `home-manager expire-generations` | removes generations of the home-manager profile; the packages are kept by the generations of the system |
| `home-manager news` | the news of the home-manager configuration, as without the option |
| `home-manager packages` | nothing, and it exits with status 1, because it looks for `home-manager-path` in `~/.nix-profile` |

The first activation with the option set removes `home-manager-path` from `~/.nix-profile`, which an earlier activation installed there.

A system-manager configuration refuses a home-manager configuration that sets this option. `topside profiles` prints where the profiles of a home-manager configuration are and what sets each.

### `caisson.drift.warn`

- **Type:** `bool`
- **Default:** `true`
- **Source:** `modules/homeManager/activation-drift/`, `modules/nvf/default/`
- **Declared in:** a home-manager configuration that imports `caisson/activation-drift`, which the home-manager `default` module imports; an nvf or nixvim configuration that imports the `default` module of its class

Whether the activation of this home-manager configuration, or `activate` of this nvf or nixvim configuration, prints a warning when it was built for a version of the configuration it is declared inside, such as its NixOS configuration or its home-manager configuration, that differs from the version that is applied.

The configuration above records what it applied in a marker file, `/etc/caisson/marker.json` for a NixOS configuration. The activation of the home-manager configuration compares the marker with the configuration above as it is in the source the home-manager configuration was built from.

The comparison leaves out the configurations declared inside the configuration above. A change to a home-manager configuration does not cause a warning, with one case apart. A home-manager configuration that sets [`caisson.useUserPackages`](#caissonuseuserpackages) has its packages installed by the NixOS configuration, and the marker of the NixOS configuration also records the digest of the `home.path` it installed. The activation of that home-manager configuration warns when its `home.path` differs from that digest. The warning does not stop the activation.

```nix
{ ... }:
{
  caisson.drift.warn = false;
}
```

Here the home-manager configuration is activated with no comparison.

See [drift detection](./lib.md#drift-detection-caissonactivation-marker-moduleshomemanagercaissonactivation-drift) for what the marker holds and what is compared.

### `caisson.profiles.selected`

- **Type:** `attrsOf str`
- **Default:** `{ }`
- **Source:** `modules/*/profile-activation/`
- **Declared in:** a NixOS, nix-darwin or system-manager configuration, a home-manager configuration or a hjem configuration that imports `caisson/profile-activation`, which the `default` module of each of these classes imports

By the variable that chooses among them, the profile a shell runs when it sets no other, as `<kind>/<name>`. `nvf/editor` is the nvf configuration declared as `editor`.

A configuration installs a program for each program of the profiles declared inside it, such as `nvim`, which runs the profile the variable names, and the default profile when the variable is unset. With one profile for a variable, that profile is the default. With several, this option names it, and the evaluation fails until it does.

```nix
{ ... }:
{
  caisson.profiles.selected.CAISSON_NVIM_PROFILE = "nvf/editor";
}
```

Here a shell that sets no `CAISSON_NVIM_PROFILE` runs the Neovim of the nvf configuration `editor`.

See [profiles](./lib.md#profiles-caissonprofile-activation).

### `caisson.forChildren.extraDefaultModuleImports`

- **Type:** `attrsOf (functionTo (listOf module))`, by class
- **Default:** `{ }`
- **Source:** `modules/generic/core/caisson/forChildren.nix`

Additions to the default selection of a class for the configurations declared inside this configuration: a function of the lib of such a configuration returning registered modules. A module listed here is registered in the composition, on `mkLib` or by a project.

```nix
{ ... }:
{
  caisson.forChildren.extraDefaultModuleImports.nixos = lib: [ lib.caisson.modules.nixos.gaming ];
}
```

A configuration that passes no `moduleImports` gets every entry named `default` followed by these, those of the levels above it first. A configuration that passes `moduleImports` gets what it selects in place of that default, and a configuration that passes `extraModuleImports` gets what that selects in addition. Definitions from several modules are concatenated.

The name says that the option adds to the default selection, as `extraModuleImports` adds to a selection. The options `defaultPkgs` and `systems` below replace the value a configuration declared inside would otherwise get.

caisson evaluates a configuration with a configuration declared inside it twice, in the childless evaluation and in the full evaluation, since what it gives is read from the result of the childless evaluation.

### `caisson.forChildren.defaultPkgs`

- **Type:** `nullOr (functionTo pkgs)`
- **Default:** `null`
- **Source:** `modules/generic/core/caisson/forChildren.nix`

The package set the configurations declared inside this configuration get by default: a function that receives the package sets available to such a configuration, as an attribute set by package config name, and returns the set to run on.

```nix
{ ... }:
{
  caisson.forChildren.defaultPkgs = pkgSets: pkgSets.stable;
}
```

Here the default for the configurations declared inside this configuration is the set of the package config named `stable`. A configuration declared inside runs on it unless that configuration, or a configuration between the two, is constructed with `defaultPkgs` or sets this option. This configuration runs on the set it was constructed with. When the option is null, the default for the configurations declared inside is the package set selection that applies to this configuration.

### `caisson.forChildren.systems`

- **Type:** `nullOr (listOf str)`
- **Default:** `null`
- **Source:** `modules/generic/core/caisson/forChildren.nix`

The systems the configurations declared inside this configuration are evaluated for. It applies to configurations that are evaluated per system, such as a NixOS configuration or a home-manager configuration. Each of them has an evaluation result for each system listed.

```nix
{ ... }:
{
  caisson.forChildren.systems = [ "aarch64-linux" ];
}
```

Set on a NixOS configuration for `x86_64-linux`, this evaluates the configurations declared inside it for `aarch64-linux`. A NixOS configuration that builds an image for an `aarch64-linux` device is an example. Set on a structural or flake level, it limits the systems the configurations inside that level are evaluated for. The systems have to be among those allowed where this configuration is declared, and a system that is not among them is refused.

When the option is null, a configuration that is itself evaluated per system has its children evaluated for its system only, so a home-manager configuration inside a NixOS configuration for `x86_64-linux` is evaluated for `x86_64-linux`. Any other configuration passes on the list it was given.

### `caisson.forChildren.unsafeCrossChildReferences`

- **Type:** `attrsOf bool`, by class
- **Default:** `{ }`
- **Source:** `modules/generic/core/caisson/forChildren.nix`

By class, whether the configurations of that class declared inside this configuration, directly or inside other configurations, read the result of the full evaluation of this configuration, with its children, in place of the result of the childless evaluation of their parent. They can then read any configuration declared inside this configuration, and a loop between them is a Nix infinite recursion, which the childless evaluation otherwise rules out. The manifest of a configuration it reaches records this configuration as `crossChildLevel`.

A setting through `caisson.forDirectChildren` beats a setting through `caisson.forNearestChildren`, which beats a setting through this option, and within one container the nearest parent that sets it wins. This option applies through every level of nesting inside this configuration. We recommend `caisson.forNearestChildren.unsafeCrossChildReferences` or `caisson.forDirectChildren.unsafeCrossChildReferences` where they cover the configurations that need the full evaluation.

### `caisson.forNearestChildren.extraDefaultModuleImports`

- **Type:** `attrsOf (functionTo (listOf module))`, by class
- **Default:** `{ }`
- **Source:** `modules/generic/core/caisson/forNearestChildren.nix`

Additions to the default selection of a class for the nearest configurations of that class declared inside this configuration. Each addition is a function of the lib of such a configuration, and it returns registered modules. A configuration of the class is a nearest configuration when no other configuration of the class sits between it and this configuration. Configurations of other classes and systems between the two do not count, so a NixOS configuration inside a structural group, or a disk layout declared inside this configuration, gets the additions.

```nix
{ ... }:
{
  caisson.forNearestChildren.extraDefaultModuleImports.nixos = lib: [ lib.caisson.modules.nixos.colmena-deployment ];
}
```

A nearest configuration that passes no `moduleImports` gets every entry named `default`, then the additions of `caisson.forChildren.extraDefaultModuleImports` of the levels above it, then these, those of the levels above first. A configuration declared inside a nearest configuration does not get them. A configuration that passes `moduleImports` selects its modules itself and gets none of them.

We recommend this option for what the nearest configurations of a class live on, such as the deployment of a node or the disk layout of a NixOS configuration, and `caisson.forChildren.extraDefaultModuleImports` for what applies to the configurations of a class at every level of nesting.

### `caisson.forNearestChildren.unsafeCrossChildReferences`

- **Type:** `attrsOf bool`, by class
- **Default:** `{ }`
- **Source:** `modules/generic/core/caisson/forNearestChildren.nix`

By class, whether the nearest configurations of that class declared inside this configuration read the result of the full evaluation of this configuration, with its children, in place of the result of the childless evaluation of their parent. It passes through configurations of other classes, as the additions above do. A configuration it applies to can read any configuration declared inside this configuration, and a loop between them is a Nix infinite recursion.

```nix
{ ... }:
{
  caisson.forNearestChildren.unsafeCrossChildReferences.nixos = true;
}
```

The upstream-compatible colmena integration sets this for `nixos`, which is how each node gets every node as colmena's `nodes` argument. A setting through `caisson.forDirectChildren` beats a setting through this option, which beats a setting through `caisson.forChildren`, and within one container the nearest parent that sets it wins. This setting connects at the nearest configurations of its class whether or not it wins there.

### `caisson.forDirectChildren.extraDefaultModuleImports`

- **Type:** `attrsOf (functionTo (listOf module))`, by class
- **Default:** `{ }`
- **Source:** `modules/generic/core/caisson/forDirectChildren.nix`

Additions to the default selection of a class for the configurations of that class declared directly inside this configuration. A configuration evaluated per system and declared here is a direct child, since a system is not a separate level. Nothing here passes through a configuration of another class, and the configurations declared inside a direct child do not get it.

A direct child that passes no `moduleImports` gets every entry named `default`, then the additions of `caisson.forChildren.extraDefaultModuleImports` of the levels above it, then those of `caisson.forNearestChildren.extraDefaultModuleImports`, then these. Where an addition here and an addition of `forNearestChildren` are the same module, matched by its key, the module is applied once, from here.

### `caisson.forDirectChildren.unsafeCrossChildReferences`

- **Type:** `attrsOf bool`, by class
- **Default:** `{ }`
- **Source:** `modules/generic/core/caisson/forDirectChildren.nix`

By class, whether the configurations of that class declared directly inside this configuration read the result of the full evaluation of this configuration, with its children, in place of the result of its childless evaluation. They can then read any configuration declared inside this configuration, and a loop between them is a Nix infinite recursion. This setting beats one through `caisson.forNearestChildren` or `caisson.forChildren`.

### `caisson.modules`

- **Source:** `modules/generic/core/caisson/modules.nix`

Export settings for each module class of the composition. caisson declares these options for each class:

- `export.enabled` (`bool`, default `true`)
- `exported` (`function -> attrsOf deferredModule`, default: the modules of the class that the composition registers itself)

The classes of the composition are the classes that the integrations declare and the classes that have a registered module. A setting for another class is refused as an option that does not exist, and so is a setting other than `export.enabled` and `exported`. A misspelled class name or setting name is therefore an error.

The selected modules are the exported modules. They are in the manifest, and
`mkLib` reads them from there for each entry of `projects`.

The exported modules are also published under `flake.modules.<class>`, and
[`caisson.flakeOutputs.modules`](#caissonflakeoutputsmodules) selects which of
them. For the `"flake"` class, the published modules are also copied to
`flake.flakeModules`.

### `caisson.modules.<class>.export.enabled`

- **Type:** `bool`
- **Default:** `true`
- **Source:** `modules/generic/core/caisson/modules.nix`

Whether to export modules for a given class.

### `caisson.modules.<class>.exported`

- **Type:** a function from the registered modules to the modules to export
- **Default:** the modules of the class that the composition registers itself
- **Source:** `modules/generic/core/caisson/modules.nix`

Function that selects which registered modules of a class to export. Receives the modules registered for the class and returns the modules to export, which are exported as the function returns them. A module that came from an entry of `projects`, registered as `<project>/<name>`, is exported only when the function names it.

The two settings of every class are held in one option, `caisson.modules`, an attribute set by class of `lazyAttrsOf raw` values, so a class that no module sets costs nothing to evaluate. Each setting is a plain value: a priority such as `mkDefault` on `exported` takes effect, and two definitions of `exported` for one class conflict rather than merge. A class with no registered module, or a key other than `export` and `exported`, is refused when the exports are read.

### `caisson.flakeOutputs.modules`

- **Type:** `function -> attrsOf (attrsOf deferredModule)`
- **Default:** `modules: modules`
- **Source:** `modules/flake/core/caisson/exports.nix`

Function that selects which exported modules are also published in the `modules` output. It receives the exported modules, as an attribute set of classes that each hold modules by name, and returns the modules to publish in the same shape. The option exists in a flake-parts configuration.

The exported modules are the modules that the `caisson.modules.<class>.exported` selectors chose. They are in the manifest, and `mkLib` reads them from there for each entry of `projects`. `mkLib` reads every exported module, whatever this function returns.

The `modules` output is for an import by hand, as `inputs.<input>.modules.<class>.<name>`. Leave a module out of the output when it only works inside an evaluation that caisson makes, because it reads the options under `caisson` or the library under `lib.caisson`.

```nix
caisson.flakeOutputs.modules =
  modules: modules // { nixos = removeAttrs modules.nixos [ "needs-caisson" ]; };
```

caisson sets the option to `_: { }`. Each module that caisson exports works only inside an evaluation that caisson makes. The `modules` output of caisson holds the empty `default` entry of the `flake` class and nothing else.

### `caisson.libOverlays.export.enabled`

- **Type:** `bool`
- **Default:** `true`
- **Source:** `modules/generic/core/caisson/libOverlays.nix`

Whether to enable lib overlay export. When enabled, the lib overlays selected by `caisson.libOverlays.exported` are exported. They are in the manifest. `mkLib` reads them from there for each entry of `projects`, and registers each as `<project>/<name>`. A lib overlay is an entry in the shape caisson registers, so there is no `libOverlays` output.

### `caisson.libOverlays.exported`

- **Type:** `function -> libOverlays`, an attribute set of lib overlays merged as one attribute set, each entry checked when it is read
- **Default:** the lib overlays that the composition registers itself
- **Source:** `modules/generic/core/caisson/libOverlays.nix`

Function that selects which registered library overlays to export. Receives the set of overlays registered via `mkLib` and returns the overlays to export. A lib overlay that came from an entry of `projects`, registered as `<project>/<name>`, is exported only when the function names it.
